- runtimes/bevy/examples/mario: `--host`/`--connect` CLI flags, per direct user request to make a LAN session as easy as possible to start. Previously getting two machines talking meant running `atlas-relay`'s standalone `examples/serve.rs` binary separately, bound correctly, then pointing each mario instance at it by hand with a full `ws://.../ws` URL plus a separate `sqld` URL. Now: one machine runs `--host` (`relay::spawn_embedded_server`, `atlas_relay::serve` in-process bound to `0.0.0.0` instead of loopback, the same in-process pattern Anvil already uses for its own relay, just LAN-reachable this time), prints the LAN IP a peer needs (best-effort via a UDP-connect trick, `local_lan_ip`) and a ready-to-copy `--connect` command; everyone else runs `--connect <that-ip>`, which derives both the relay and `sqld` URLs from the one address instead of needing both spelled out. `--relay`/`--sqld` still override either individually for a session whose topology doesn't put both services on one machine. Also fixed a real startup race this surfaced: connecting to the relay was a single attempt with no retry, so a `--host` instance dialing its own just-spawned embedded server (or a `--connect` peer starting slightly before the host finished binding) could lose the race and silently fall back to local-only play; `relay.rs`'s `connect_with_retry` now retries for up to 3s before giving up.
- runtimes/bevy/examples/mario: real cross-instance combat, per direct user request ahead of a remote playtest tonight. Previously, hit detection only ever checked pairs of *locally-owned* gamepads on one instance (`relay.rs`'s own top comment said as much) — a swing could never connect against a player on a different machine at all, only their position was synced. New second WebRTC data channel (`relay.rs`'s `COMBAT_DATA_CHANNEL_LABEL`/`CombatEvent`), reliable and ordered unlike the existing lossy 30Hz position channel, since a dropped "you died" permanently desyncs which player is alive in a way a dropped position tick never does. Attacker-authoritative: the instance whose local swing connects against a remote-tracked target's last-known position decides the hit and broadcasts a `CombatEvent`; the target's own instance is the only one that actually applies the death to its own player (`physics.rs`'s new `apply_local_death`, factored out of and shared with the existing local-vs-local path). Known scope cut, not yet done: a remote player's death isn't reflected in how a *third* instance renders them (`main.rs`'s remote-render path still hardcodes `alive: true`, since `PositionPacket` carries no combat state) — the dying player's own screen and the attacker's own hit feedback both work correctly, only a spectator's visual of someone else's death doesn't yet.

## 2026-08-21
- runtimes/bevy/examples/mario/physics.rs: decomposed `update_mario_physics` — one large system doing input-reading, physics stepping, sfx-triggering, combat/hit-detection, collision resolution, and network-snapshot writing all inline in one per-gamepad loop plus three trailing loops — into seven small, focused systems (`reconcile_gamepad_ownership`, `handle_cheat_menu_input`, `step_mario_physics`, `apply_incoming_combat_events`, `resolve_mario_hits`, `resolve_mario_collisions_and_grounding`, `publish_local_mario_snapshot`), chained in `main.rs` in the exact order the original code's own internal sequencing already ran in. Per direct user architectural feedback: a single system silently sequencing this many concerns in its own control flow gives Bevy's scheduler nothing to reason about — it's a hand-rolled update loop wearing one `System` label, not real ECS decomposition, and was flagged as the likely root cause behind this session's earlier render bugs being so easy to introduce. Correctness-preserving, not a rewrite: four of the seven (combat-apply, hit-detection, collision-resolution, snapshot) were already separate trailing loops in the original function, a mechanical extraction; the other three split what used to be one per-gamepad loop (menu-toggle, then input-decode+step+registration) — verified safe by reading the actual control flow rather than assuming: the pause-menu's Start-toggle now resolves for *all* gamepads before any gamepad's physics-step decides whether to skip for "menu open," removing a real order-dependent quirk the original interleaved loop had (arguably a small correctness improvement, not just a decomposition), and the "a new gamepad plugged in while the menu is open doesn't get registered until it closes" behavior is preserved exactly (the same ownership + cheat-menu-open guards are re-checked in `step_mario_physics`). Explicitly did not migrate `GameState.mario` off `Arc<RwLock<Vec<...>>>` onto real Bevy components/queries this pass — every new system still goes through the same shared lock via `Res<GameState>`, so Bevy's scheduler still can't actually parallelize any of this; `.chain()` enforces an order the scheduler has no way to discover on its own. That bigger migration is the real prerequisite for both true scheduling benefit and the "someone else's app plugs in a few systems" reusability goal discussed earlier this session — logged as real, separate, higher-risk follow-up work, not attempted here.

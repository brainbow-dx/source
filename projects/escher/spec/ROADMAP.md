# Escher Roadmap

Living checklist toward "fully functional, polished." Update as work lands — check items off, add new ones, don't let it drift stale. Rough, not exhaustive; see linked proposals in `spec/.agents/proposals/` for design detail behind any item. `[x]`/`[ ]` is the whole status signal — done or not; a state a checkbox can't express (blocked, high priority) is called out with a bold text label instead, never an emoji next to the checkbox.

Last updated: 2026-08-18.

- [ ] Bevy surface reconciliation (currently full teardown/rebuild every draw — see `proposals/generalized-reconciliation.md` Phase 3)
- [ ] Web/DOM surface reconciliation (Phase 2 of the same proposal)

- [ ] Terminal reconciliation — likely skip per the proposal's own Phase 4 note (ratatui's own diffing may already be enough)
- [x] **Standing goal, logged 2026-08-18**: building a `Scaffold` tree should feel as natural and terse as JSX does for a React developer. First quick pass, same day: dropped the `with_` prefix from every builder method (`with_style`/`with_slot`/`with_content`/`with_handler`/ `with_element`/`with_state`/`with_debug`/`with_overlay` became `style`/`slot`/`content`/ `handle`/`element`/`state`/`debug`/`overlay`) across the whole workspace, since the API reads as composition, not a builder pattern that needs the prefix to read as fluent. Closure-per-slot (`slot::<S>(|s| ...)`) is a deliberate design, not verbosity to remove: it makes misusing the arena/identity model structurally impossible (a built child can't be reused across slots or held across draws), it's lazy (a skipped slot's closure never runs), and because a closure is just a value of type `FnOnce(Scaffold) -> Scaffold`, a named function, a closure, and a future FFI/scripting-provided callback are all the same shape to `slot` — enabling extraction into reusable, independently testable functions for free. Not up for redesign. The real remaining noise is repeated `.style(...)` chains on one node. Direction agreed 2026-08-18: not a Tailwind-style string utility-class system (would reintroduce the stringly-typed lookups this codebase already wants to move away from, see the styleguide item below) — instead, small composable Rust functions that mutate a style block, applied to whatever scaffold takes it, the same reusability goal Tailwind's utility classes serve but type-checked and IDE-navigable. Worth borrowing from Tailwind: a curated numeric spacing/size scale, paired with the existing styleguide system rather than a new mechanism. Design not started.

- [x] **Fixed 2026-08-17**: new-tab-creation lag, the actual fix. Root cause: `apply_browser_ navigation` (adds the tab) and `attach_pending_tab_webviews` (creates its native `WebView`) ran in the same `Update` tick — `WebView::attach`'s synchronous native-view-creation cost (real, worse for the first webview a process creates) blocked that frame from ever presenting, so the new tab row never visibly appeared until the attach was already done, no matter how "instant" adding it to `BrowserState` was. Fixed with `Tab::attach_deferred`: the first tick a tab has no `WebView` yet, skip attaching and let that frame present (tab row visible, `Tab::loading` now defaulting `true` from `open_tab` instead of only becoming `true` once a `WebView` exists to ask); the *next* tick does the real attach. Also fixes a second, separate bug found alongside it: closing the last tab left its `WKWebView` still attached and visibly showing stale content — `escher_webview::WebView`'s own doc comment already claimed "dropping it removes the webview from the window," but the macOS backend never implemented that; `WebViewInner` now has a `Drop` impl that actually calls `removeFromSuperview()`.
- [ ] Sidebar (tab strip) drag-to-resize: drag the strip's edge to resize between a reasonable min/max width, collapsing (not clamping) once dragged below the minimum — today's sidebar only has the binary collapse/expand toggle (`ToolbarEvent::ToggleSidebar`, `TabStripState::collapsed`), no drag handle or width persistence yet.
- [ ] Real eased/animated hover & state transitions (needs a timer-driven redraw loop — none exists yet; deliberately deferred, instant-swap only so far)
- [ ] Dark-mode verification signed-in (Google/YouTube dark theming looked gated behind account state, not `prefers-color-scheme` — unconfirmed, needs a real signed-in check)
- [x] **Fixed 2026-08-16**: the reported multi-second-to-multi-minute hang on dragging the overlay / typing / any input — root-caused (not just reproduced) via code inspection after the user described the exact trigger. Real cause: every `store.save_*` persistence write (`save_message`/`save_task`/`save_overlay_bounds`) ran via a bare `runtime.block_on(async { ...})` directly on the render thread with **no timeout** — `persistence::CONNECT_TIMEOUT` only ever covered the initial connect, not any later write, despite its own doc comment already warning "the connect/sync calls below have no timeout of their own." A slow/wedged `sqld` (documented history of instability in this repo — see `changelog.md`'s 2026-08-13 "sqld crash loop" entry) would hang the *entire UI* for however long the underlying TCP call took to fail, unbounded, matching "inconsistent, seconds to minutes" exactly — triggered by drag (the overlay-position debounced save) and by *any* Enter-key submission (every input branch persists a `User` message the same way, including the two new ones added earlier tonight for `/shape`/shell-passthrough). Fixed via a new `SAVE_TIMEOUT` (750ms) + `block_on_with_timeout` helper (`main.rs`, right after the `persistence` module) that every one of those five call sites now goes through. **Turned out to be two separate bugs, both now fixed and both measured, not just reasoned about:**
      1. The persistence-blocking bug above — further hardened same night: every write now routes through one ordered background writer task (`AppState::persistence_writes`, an `mpsc` queue) instead of independent concurrent spawns, so concurrent writes can never race into the single shared `sqld` `Connection` regardless of what its own concurrency guarantees actually are. Overlay-bounds writes specifically get coalesced (a queued burst collapses to just the latest position) since window position is cosmetic, not real data — chat messages/tasks are still persisted individually, in order, every time.
      2. **A second, unrelated bug, found by actually testing, not just re-reasoning about the first fix**: user reported the stutter was "a bit better" but still bad specifically *while moving fast*. Root-caused live with a real instrumented build + a synthetic mouse-drag flood injected via `tmux send-keys` (SGR mouse escape sequences) — confirmed 42 queued `Drag` events triggered 42 full scaffold re-renders in one Bevy tick (each render is a full rebuild — no reconciliation yet, see M0), 122.5ms total in one synchronous block. Fixed in `escher-terminal`'s `TerminalSurface::draw_with_poll_timeout` (`runtimes/terminal/src/surface.rs`): consecutive `Drag(Left)` events now coalesce to the latest one before dispatch, since `Up`'s own handler resolves the drag's final position from the `Up` event's own point, not the preceding `Drag` — every other event kind still dispatches one at a time, unchanged. Re-measured with the identical synthetic burst after the fix: 2 draws, ~1ms total, down from 42 draws / 122.5ms. `cargo check --workspace` clean.
      3. Wrote up both incidents' lessons in the new `spec/.agents/principles.md` (linked from `AGENTS.md`) — verify empirically rather than reasoning from a fix that only addressed part of a reported symptom, among others.
      4. **Fixed 2026-08-17, the actual remaining half of incident 2**: the Drag-coalescing fix above reduced *dispatches* per render call, but did nothing to cap *render* count — user noticed (via the fps counter, itself fixed the same day to stop freezing while idle — see `AppState::frame_times`) that a sustained hard drag spiked measured fps well past 100, sometimes 250+. Root cause: `apps/anvil`'s `assistant_terminal_draw` had `MAX_DRAWS_PER_TICK = 64`, willing to render up to 64 full frames back-to-back within a single Bevy tick to drain a fast-arriving queue — during a sustained drag the queue never empties, so it legitimately used most of that budget, in a few milliseconds, every tick. A terminal has no reason to repaint faster than ~60fps; the rest was pure waste. Fixed by dropping the constant to 3 (drains a normal typing burst in one tick, no more) *and* changing `escher-bevy`'s `spawn_input_watcher` to re-send `WakeUp` every ~16ms for as long as the input queue stays nonempty, instead of one wake per burst and then silence — the two changes are paired, not independent: lowering the per-tick cap alone would have reintroduced the exact stall incident 2's `Drag`-coalescing fix was built to avoid, since nothing would prompt a following tick to finish draining a long burst. `cargo check -p escher-bevy -p escher-anvil --bin anvil` clean; **live-verified 2026-08-17**: user confirms fps now caps around 120 (not a hard 60 — `MAX_DRAWS_PER_TICK = 3` still allows up to 3 real renders per ~16ms re-wake, not strictly 1; expected, not a bug) and, unprompted, reports browser tab-opening got noticeably snappier too. That second effect isn't a separate fix — terminal drawing and AppKit/webview handling share one process and one main thread, so every one of the ~200 wasted redundant repaints/sec this fix eliminated was CPU time that `WebView::attach`/toolbar redraws/event dispatch were also competing for. Real candidate for the single biggest perf bottleneck found in this app to date, precisely because it was burning the one shared resource everything else here also depends on.

None of this is built yet — no code today reads `Cargo.toml` metadata for Anvil's own config, and Anvil isn't structured as a mountable library today either (it's a single `apps/anvil` binary crate) — that restructuring is itself a real prerequisite this note doesn't yet scope.

## M11 — Native Cross-Platform Runtimes

**Standing goal, stated 2026-08-18**: real native support across Android, Windows, Linux, and the full Apple OS family (macOS today, plus iOS/iPadOS/tvOS/visionOS/watchOS) — explicitly not a web-view/browser-shell shortcut on any of these. Verified against the actual codebase before writing this down, not assumed:

- [x] macOS — `runtimes/appkit`, real Rust bindings (`objc2`/`objc2-app-kit`/`objc2-web-kit`) directly against AppKit/WKWebView. No Swift anywhere in this repo, despite how it's often described in conversation — worth stating plainly since that description is wrong.
- [ ] iOS/iPadOS/tvOS/visionOS/watchOS — no code, not scoped. AppKit doesn't run on any of these; would need the UIKit-family equivalent of `runtimes/appkit`'s work, likely its own `runtimes/uikit` (or similar), not a rehost of the AppKit backend.
- [ ] Windows — no native-chrome backend (`runtimes/webview`'s own doc comment already says so plainly: "macOS only for now"). The layers underneath it are *not* blocked, though: `escher-bevy` (Bevy + winit) and `escher-terminal` (ratatui + crossterm) have zero macOS-specific gating and are genuinely cross-platform upstream — Anvil's terminal UI (transcript, tasks, everything that isn't the native browser chrome) is very likely already running on Windows/Linux today, untested but with nothing macOS-specific in the way. The native browser-chrome/webview layer itself is unbuilt; target API is WebView2 (Microsoft's own embeddable webview, closely analogous to WKWebView) — comparable *amount* of new work to what `runtimes/appkit`/`runtimes/webview` took, not reusable code, but a clear target.
- [ ] Linux — same gap and same underlying-layers-already-portable situation as Windows; target API is webkit2gtk.
- [ ] Android — no code anywhere (`runtimes/` has no Android analog, confirmed by grep). Bigger gap than desktop: Android has no AppKit/WebView2/webkit2gtk equivalent to target directly — a real native surface means a from-scratch renderer against Android's own toolkit (View/Kotlin or Jetpack Compose), the same category and scale of work `runtimes/appkit` already represents, not a port of it. Nothing scoped yet.
